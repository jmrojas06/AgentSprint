## Description

Hallazgo de review de TK-17: `packages/core/src/storage.ts` `_atomicWrite` usa nombre tmp fijo `${file}.tmp` sin lock. Dos procesos escribiendo a la vez pueden colisionar en el mismo tmp o perder entradas por el read-modify-write de `appendLearningsSection`. Fix: tmp único por escritura, cleanup en error y lock simple por archivo para secciones críticas.

## Acceptance criteria

- [x] El nombre del archivo temporal es único por escritura (incluye pid y bytes aleatorios), evitando colisiones entre procesos
- [x] La escritura usa rename atómico y limpia el archivo temporal en error (try/finally)
- [x] Las secciones críticas read-modify-write (appendLearningsSection, setTaskStatus) están protegidas contra escritura concurrente sin perder entradas
- [x] No cambia el formato de ningún archivo persistido (.md, .yaml, .json)
- [x] Tests que simulan escritura concurrente (dos llamadas paralelas a appendLearningsSection / updateTask) verifican que no se pierde ninguna entrada y que no quedan archivos .tmp residuales

- [2026-10-21T19:44:32.000Z] (fixer) Fixed the blocking stale-lock finding. Root cause: withFileLock (packages/core/src/filelock.ts) created `${file}.lock` with no owner information and had no recovery path, so a writer SIGKILLed inside the critical section left a lock that made every later write wait 2s and throw. Fix: the lock now stores `{pid, host, at}`; on EEXIST the waiter removes the lock and retries the exclusive `wx` create when it is stale: its owner pid is dead on this host (`process.kill(pid, 0)` throws ESRCH), it has no owner and is older than the 2s write timeout (legacy/mid-create), or it is older than FILE_LOCK_STALE_MS (10s, which also covers pid reuse). A live owner's lock is never taken. Stealers serialize on a short-lived `${file}.steal.lock` and re-check staleness inside it, so two waiters that saw the same dead lock cannot delete the lock the first one just took.
